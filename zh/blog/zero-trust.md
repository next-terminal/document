# 从 VPN 到零信任：Next Terminal 的统一访问入口实践

很多团队搜索**零信任**或**VPN替代**，并不是要立即推翻现有网络，而是希望解决一个具体问题：员工、外包人员或值班工程师需要访问内网服务器、Windows 桌面、数据库和 Web 系统，却不想把整个网段一次性暴露给每个登录者。**开源堡垒机**可以把“进入网络”改成“按资产授权访问”，让连接、身份、权限和运维审计集中在一个入口中。本文以 Next Terminal 当前 v3.7.2 文档为边界，说明逐步迁移方法，也帮助评估 **JumpServer 替代**或 **Teleport 替代**的团队建立验证清单。

## VPN 的便利与边界

传统 VPN 的优点很明确：部署一个入口，用户获得地址后即可使用原有 SSH、RDP 或浏览器工具。但网络可达不等于业务授权。VPN 解决的是“能否到达某个网段”，而不是“某个人今天是否应该访问某一台资产”。当权限变化、人员离职、客户环境隔离或审计取证发生时，单纯依赖网络层规则往往会出现三类问题：

1. **访问范围过宽**：一个账号进入网段后，可能可以探测并连接多个并未授权的地址。
2. **身份与连接脱节**：VPN 登录记录证明用户进入过网络，却未必能直接对应到具体资产和操作。
3. **跨网络维护复杂**：不同机房、VPC 和客户现场需要重复配置路由、端口映射或专线。



## 先画清楚访问边界

开始改造前，建议按协议、网络位置和风险分组，而不是给所有设备套同一个策略：

| 资产类别 | 常见协议 | 访问主体 | 主要控制点 |
| --- | --- | --- | --- |
| Linux 与网络设备 | SSH | 运维、值班人员 | 用户/组授权、命令审计 |
| Windows 服务器 | RDP | 运维与桌面支持 | 资产授权、会话录像 |
| 数据库 | 数据库协议 | DBA、应用团队 | 专门账号、SQL 审计 |
| 内部管理系统 | HTTPS/Web | 员工、外包人员 | Web 资产、MFA、mTLS |
| 客户现场或 VPC | SSH/RDP/VNC | 指定项目成员 | 安全网关、最小可达范围 |

Next Terminal 的[资产管理](/zh/usage/asset)支持将不同协议的连接信息集中登记，再通过授权关系决定谁可以访问。这个模型的关键不是把所有设备都搬进来，而是先选择一组有代表性的资产：一台 Linux、一台 Windows、一个数据库或 Web 系统，以及一个隔离网段中的目标。这样既能验证访问链路，也能避免迁移初期影响全部业务。

## 用安全网关连接隔离网络

如果堡垒机服务端无法直接访问客户内网或 VPC，传统办法通常是为每台资产开放端口，或者让用户通过 VPN 进入更多网段。Next Terminal 的[安全网关](/zh/usage/agent-gateway)是部署在目标网络中的 Agent：它主动与服务端建立 WebSocket 通信，服务端在转发访问时通过该网关连接内网目标。

这一方式的落地步骤可以拆成三步：

1. 在目标网络准备一台能够访问服务端 Web 端口的设备，安装并注册安全网关。
2. 在服务端确认网关在线，再添加 SSH、RDP 或 VNC 资产，并选择对应网关。
3. 使用授权账号访问资产，验证连接、断线重连和审计是否符合预期。

注册命令和参数应直接从管理页面复制，并按照[安全网关配置文件](/zh/usage/agent-gateway-config)配置服务端地址、代理或自动更新选项。不要把网关 token 写进公开脚本或提交到代码仓库；生产环境还应确保服务端启用 HTTPS。

安全网关并不是一个无限制的网络扫描器。它只应承担从网关所在网络到已登记目标地址和端口的连通职责，资产本身仍要通过 Next Terminal 的授权关系保护。迁移验证时，可以在网关所在主机测试目标端口，并在堡垒机管理页面检查网关在线状态；这样能够区分“网关未注册”“网关到目标不通”和“用户没有资产权限”这三种不同故障。

## 从网络许可转向资产授权

零信任入口的第二个变化，是把权限写成可检查的业务关系，而不是只靠防火墙放行。建议采用“用户或用户组—资产或资产组”的授权结构，并为不同职责分开账号。例如，值班人员只访问生产 Linux 的只读维护资产，DBA 才能访问数据库，外包用户只访问项目组资产。权限调整时修改授权关系即可，不需要重新给整个网段划分 VPN 路由。

访问前还要确认几个细节：用户是否已经完成登录认证，目标资产的凭证是否有效，资产是否经过安全网关，以及当前访问是否需要额外的 MFA。Next Terminal 提供 Passkey 和 TOTP 等身份增强能力，具体配置可参阅[通行令牌（Passkey）](/zh/usage/passkey)与 [2FA（TOTP）](/zh/usage/otp)。对于公开入口或高风险资产，建议把强认证作为访问策略的一部分，而不是仅在员工第一次登录时验证一次。

可以用下面的伪流程检查一次访问是否真的符合边界：

```text
用户登录 -> 完成额外身份校验 -> 匹配用户/资产授权
      -> 选择可用安全网关 -> 连接目标协议与端口
      -> 记录访问事件 -> 按协议生成可回放审计
```

这条链路中每一步都应能在试点中被观察到。尤其不要只验证“能连上”，还要验证未授权用户不能连接、错误网关会明确报错、资产删除或撤销授权后旧入口不会继续提供访问。

## 统一入口不等于只有浏览器

零信任访问的目标是统一控制面，不是强迫所有人只使用一种客户端。日常临时维护可以使用 Web 终端；需要脚本、跳板习惯或本地工具的工程师，可以按照[资产访问](/zh/usage/access)和 SSH 代理文档使用本地客户端。Windows 运维人员也可以验证 RDP 代理与本地客户端的协作方式。统一入口负责认证、授权和审计，本地工具负责提供熟悉的操作体验，两者并不冲突。

Web 资产也应纳入同一套边界。内部 Grafana、监控面板或管理后台不必随着 VPN 把整个内网交给用户，而可以作为 Web 资产登记，并结合 HTTPS 与 mTLS 控制入口。数据库则应使用独立资产和专门凭证，避免把数据库端口当作普通 TCP 端口随意开放。这样做的价值在于，SSH、RDP、数据库和 Web 的授权对象可以统一管理，审计人员也能在同一个系统中按用户、资产和时间回查。

## 运维审计要验证什么

**运维审计**不是“页面上有日志”就算完成。试点阶段至少准备四个可复现动作：普通登录、一次成功的 SSH 或 RDP 操作、一次文件或数据库操作（按实际协议选择）、一次撤销授权后的失败访问。逐一检查以下结果：

- 事件是否关联到明确用户，而非共享账号或模糊 IP；
- 资产、协议、开始时间和结束时间是否可检索；
- 图形会话是否能回放，回放内容是否足以判断操作位置；
- SSH 命令、文件操作或数据库会话是否按当前版本实际能力记录；
- 录像和日志的存储位置、保留周期与备份策略是否符合团队制度。

关于更完整的控制项映射，可参考[合规与审计](/zh/usage/compliance)。不要为了满足某个模板而宣称系统自动满足全部法规要求；等保、ISO 27001 或企业内审都有各自的范围，最终应以组织制度和实际测试结果为准。Next Terminal 能提供技术控制点，审计结论仍需要由负责人员确认。

## 一条可控的迁移路线

从 VPN 迁移到零信任，建议分阶段推进：

### 第一阶段：建立基线
记录当前 VPN 用户、网段、资产、常用协议和审计缺口。挑选低风险测试资产，确认备份、回滚和原有紧急入口仍然可用。

### 第二阶段：接入核心资产
按用户组和资产组导入少量 SSH/RDP 资产，配置凭证和授权。先不改变所有网络策略，用并行方式比较连接成功率、操作耗时和排错路径。

### 第三阶段：覆盖隔离网络
在一个 VPC 或客户现场部署安全网关，验证服务端到网关、网关到资产两段链路，并准备网关离线时的告警和人工处理流程。

### 第四阶段：收紧入口
当授权和审计稳定后，逐步减少普通用户对 VPN 网段的直接访问，只保留确有必要的网络级通道。高风险资产增加 MFA，外包账号设置明确的资产范围和生命周期。

### 第五阶段：持续复盘
每月检查离职账号、长期未使用授权、失败访问、录像存储和恢复演练。零信任不是一次性上线项目，权限和资产都会随组织变化。

### 迁移中的几个常见误区

第一，不要把“所有流量都经过一个入口”误解成“所有用户共享一个账号”。统一入口更需要独立身份，才能让授权和审计保持可追溯。第二，不要只在网络正常时测试，应该主动验证网关离线、凭证失效、授权撤销和会话中断等情况。第三，不要把审计当成上线后的补充工作，录像存储、日志保留和恢复演练应在试点阶段就确定。最后，迁移范围要有明确的回滚边界：保留原有紧急通道，但限制其使用对象并记录使用原因，避免临时措施永久化。

## 总结

从 VPN 到零信任，不是把网络边界换成一个新名词，而是把访问控制从“进入某个网段”细化为“某个身份在当前条件下访问某个已授权资产”。Next Terminal 作为轻量的**开源堡垒机**，可以用统一控制面承接 SSH、RDP、VNC、数据库和 Web 资产，并通过安全网关连接隔离网络；对评估 **JumpServer 替代**或 **Teleport 替代**的中小团队，最值得验证的是这条链路能否在自己的资产、身份和审计制度中稳定闭环。

建议先用一组真实但可控的资产试点，再依据授权边界、网关稳定性、用户体验和审计证据决定下一步，而不是先承诺一次性替换全部 VPN。准备开始评估时，可查看 [Next Terminal 定价](https://www.next-terminal.com/pricing)，并在[在线演示](https://demo.next-terminal.com)体验统一入口；正式部署请从[容器安装](/zh/install/container-install)开始。
