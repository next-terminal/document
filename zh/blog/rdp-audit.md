# RDP 会话审计与录像回放：中小团队如何满足运维合规

对很多中小团队而言，**堡垒机审计**的痛点不在“有没有 Windows 服务器”，而在“RDP 运维是否可追溯”。人一多、资产一多，`Administrator` 共用、操作无记录，遇到故障或审计时无法定位“谁在何时做了什么”。本文以 **RDP审计、会话录像与运维审计** 为主线，介绍如何用 Next Terminal 这款轻量**开源堡垒机**落地可回放、可取证的 RDP 合规闭环，并说明它作为 **JumpServer替代 / Teleport替代** 在中小团队场景的取舍。

## 为什么中小团队更需要 RDP 会话审计

“等保”“内审”不是大厂专利。只要涉及客户数据、财务系统或生产环境，甲方、审计方通常会问三句话：谁能连哪台机器、操作能否追溯到人、证据能不能留存。RDP 场景尤其高危：图形化操作难以用命令日志还原，剪贴板与磁盘重定向可能带出敏感数据。

常见现状与风险：

- **账号共用**：多运维共用同一本地账号，事后无法定责。
- **直连内网**：RDP 端口映射到公网或 VPN 全网互通，缺乏按人按资产的细粒度授权。
- **无录像**：只有登录日志，没有会话录像与回放，审计时缺少直接证据。

Next Terminal 的思路是把“身份认证—授权—审计录像”收敛到统一入口，不改变运维习惯的前提下补齐**堡垒机审计**能力。快速部署见 [容器安装](/zh/install/container-install)，资产与授权模型见 [资产管理](/zh/usage/asset)。

## 合规到底审什么：5 项控制项对照

审计方的问题可归纳为 5 类，Next Terminal 的能力映射如下。完整对照见 [合规与审计](/zh/usage/compliance)。

| 控制项 | 审计常问 | Next Terminal 对应能力 |
| --- | --- | --- |
| 访问控制 | 谁在何时从何地能访问哪台 Windows 资产 | 资产按人/组授权，登录策略约束来源与时段 |
| 身份认证 | 访问前如何验证身份 | Passkey/TOTP/LDAP/OIDC，mTLS 可前置于反向代理 |
| 操作可追溯 | 每次 RDP 操作能否追溯到人 | 会话关联到账号与资产，文件与操作日志可查询 |
| 证据留存 | 录像与日志是否可留存、防篡改、易调阅 | 在线会话 + 离线录像回放，支持 S3 归档与长期留存 |
| 最小权限与拦截 | 高危操作能否事前管控 | 访问策略按资产隔离，敏感操作结合审批与审计联动 |

> 小团队落地建议：先做到“人—资产可关联、会话可回放、录像可保存 180 天”，再逐步叠加 MFA 与 mTLS。不要一上来就追求全量阻断，审计更看重“可证明的闭环”。

## Next Terminal 如何做 RDP 审计与录像

Next Terminal 提供两条 RDP 接入路径，审计链路一致，按团队习惯二选一：

- **Web 端 RDP 访问**：浏览器直接打开远程桌面，零客户端，适合临时运维与受限终端，无需暴露额外端口。
- **RDP 代理服务器（本地客户端）**：在 [RDP 代理服务器](/zh/usage/rdp-server) 开启后，用户为已授权的 RDP 资产下载 `.rdp` 文件，用 Windows 自带远程桌面或 Microsoft Remote Desktop 通过票据 `NTICKET` 接入代理，再由堡垒机代理到真实资产。适合需要剪贴板、磁盘重定向、RemoteApp 的场景。

两者的共同点是：**权限校验与会话创建均在堡垒机完成**，用户无需知晓目标 Windows 账号密码，会话状态进入审计与录像策略。票据默认 300 秒有效、一次性使用，过期或已使用需重新下载。

接入方式与网关的关系：若 RDP 资产在内网或多云 VPC，可通过 [安全网关](/zh/usage/agent-gateway) 建立反向隧道，资产配置时选择所属网关即可统一入口，无需在每个机房做端口映射。网关配置细节见 [安全网关配置文件](/zh/usage/agent-gateway-config)。

## 实战：3 步开启 RDP 会话审计与回放

### 步骤 1：准备资产与授权

1. 在资产管理中创建协议为 `RDP` 的资产，填写地址、端口与凭据。
2. 将资产授权给具体用户或用户组，避免共用账号。
3. 若资产在内网，绑定对应的安全网关。

> 授权是审计的前提——会话必须能关联到“人”。先做 [资产管理](/zh/usage/asset) 的人—资产矩阵，再开录像。

### 步骤 2：选择接入方式并开启 RDP 代理（如需本地客户端）

仅 Web 访问无需额外端口；如需本地 RDP 客户端，需在 `docker-compose.yaml` 中映射代理端口并在系统设置中开启服务：

```yaml
services:
  next-terminal:
    ports:
      - "8088:8088"
      - "3390:3390"  # RDP 代理，默认 3390
```

系统设置 > RDP 代理服务器：开启服务、设置监听地址（默认 `0.0.0.0:3390`）、对外访问地址（建议显式填写客户端可达域名如 `rdp.example.com:3390`）、票据有效期（60–3600 秒，默认 300 秒）。修改后重建容器使端口生效：

```bash
docker compose up -d --force-recreate next-terminal
```

证书在首次启动时自动生成于 `data/rdp-proxy/server.crt` 与 `server.key`，客户端首次连接的自签名提示属正常现象。

### 步骤 3：验证审计与回放

1. 用被授权账号登录 Next Terminal，下载 RDP 资产的 `.rdp` 文件并连接。
2. 在会话管理中查看在线会话，断开后检查离线录像是否生成。
3. 随机抽取一条录像完成回放，确认画面、时长与操作可还原。

若下载或连接失败，按 [RDP 代理服务器](/zh/usage/rdp-server) 的排查清单检查授权、票据时效、端口映射与对外访问地址。

## 录像存储与留存：本地还是 S3

录像默认落盘到本地 `data` 目录，适合单机或演示；生产环境建议归档到 S3 并开启版本与对象锁，以满足长期留存与防篡改要求。HA 场景下，多个实例通过共享存储或 S3 保证录像一致性，架构与 Checklist 见 [主备高可用部署](/zh/install/ha-primary-standby-guide) 与 [生产级 Checklist](/zh/install/ha-production-checklist)。

建议留存策略：

- **留存期**：≥180 天，或按甲方/行业制度执行。
- **分级存储**：热数据本地、冷数据 S3 归档，定期演练恢复。
- **完整性**：对离线录像做转码与校验，访问日志与录像相互印证。

> 审计关注“证据链”，不仅是“有录像”。把录像、访问日志、授权矩阵与备份演练记录放在一起，才能形成可出示的合规材料，详见 [合规与审计](/zh/usage/compliance)。

## 给审计员看什么：一条可出示的证据链

陪审时，建议按以下清单准备材料，每项都能在 Next Terminal 后台直接导出或演示：

1. **用户—资产授权矩阵**：谁能访问哪台 RDP 资产，何时授权。
2. **会话样例**：一条 RDP 会话的起止时间、来源 IP、关联账号与资产。
3. **录像回放**：一条完整回放，证明操作可还原。
4. **访问日志与文件操作日志**：与录像相互印证的关键操作。
5. **身份与网关配置**：MFA/mTLS/IdP 配置与安全网关拓扑。
6. **备份与 HA 演练记录**：证明留存与可用性经过演练。

中小团队用这套材料即可覆盖多数等保与内审的**运维审计**访谈，无需为了一次审计引入重型平台。

## 常见坑位与避坑

- **对外访问地址留空**：在 NAT/反代/容器映射后，自动推导的地址可能不可达，务必显式填写客户端真实可达地址。
- **票据复用**：`.rdp` 票据一次性有效，重连或等待超时后需重新下载，不要长期保存旧文件。
- **端口未映射或安全组未放行**：`3390` 未映射或防火墙未放行会导致本地客户端无法连接，先用 `telnet rdp.example.com 3390` 验证。
- **仍用共用账号**：堡垒机授权到人后，应在 Windows 侧配合独立账号或审计到堡垒机账号，避免“审计到堡垒机、追溯不到人”。

## 总结

对中小团队，**RDP 会话审计与录像回放**的关键不是功能堆砌，而是“可证明”。Next Terminal 以轻量部署、统一入口与可回放的会话审计，帮助团队以较低成本补齐**堡垒机审计**与**运维审计**合规项；相较重型方案，它作为 **JumpServer替代 / Teleport替代** 更适合 5–50 人、资产数百台以内的私有化场景。
